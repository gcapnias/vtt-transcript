# How real projects build, version, and release `bun build --compile` binaries in GitHub Actions (tracking issue gcapnias/yt-transcript#22)

Research date: 2026-11-09. Bun 1.4.4 is the latest release (`gh release list --repo oven-sh/bun`). Labels: **[V]** = verified by reading the workflow file, issue, or doc named; **[I]** = my inference, no source states it. Scratch copies of the workflow files were fetched to `.scratch/wf/` (gitignored); permalinks below use the commit SHA returned by `gh api repos/<repo>/commits?path=<file>`.

## Executive summary

- **The boring, proven pattern is a tag-push workflow**: `on: push: tags: ['v*']`, a matrix that runs `bun build --compile --target=<bun-target> ... --define 'VERSION="<x.y.z>"'` and `softprops/action-gh-release@v2` to attach the binaries. Of the 27 Bun-compile workflows fetched whose trigger I read, 15 are plain tag-push, 3 are release-please, 1 is changesets, 1 is a push to `master` gated on a `VERSION` file, and 2 trigger on a GitHub `release` event. **[V]**, counts below.
- **The version source is almost always `package.json` (hand-bumped) plus a tag.** Three sub-variants: (a) tag is the source and CI rewrites `package.json` from it (muxinc/cli); (b) manual bump plus tag, with a CI guard that fails when tag and `package.json` differ (shaharia-lab/slackcli, fal-ai-community/genmedia-cli); (c) the number is injected with `--define` or a generated file (linear/linear-release, ubie-oss/n8n-cli, mkdnsite, capa). Variant (b) is the closest match to this repo's hand-edited `0.3.0` plus annotated tags.
- **GitVersion: 0 hits.** A `gh search code` for `bun build --compile` together with `GitVersion` or `gittools/actions` returned no workflow. `git describe` appears in Bun's own docs as the example for `--define`, but I found no workflow that uses it for a released version. **[V]** for the searches, N is small (search is the legacy GitHub engine, results are not exhaustive).
- **A single Linux runner can build every target** (Bun docs), and 6 of the sampled repos do exactly that. The exceptions are Windows file properties and icon (the flags do not work when cross-compiling) and macOS signing (needs `codesign` on macOS or `rcodesign` on Linux).
- **Nobody in the sample enforces "only `main` releases" with a `v*` tag trigger**, because a tag trigger fires for a tag on any branch. Projects that need it trigger on a push to `main` (release-please, gbrain). I found no sampled repo that checks branch ancestry of the tag. That check is **[I]** for this repo.
- **Pin Bun.** The sampled projects that hit trouble pinned an exact Bun version (slackcli 1.4.1, gbrain 1.4.4, thunderbolt 1.4.4, others 1.3.11 to 1.3.14), because 1.3.12 shipped corrupt macOS signatures and 1.4.0 has an open macOS 27 SIGKILL report.

## 2. Getting the version into the binary (Bun docs)

- **`--define` is supported and documented for `--compile`.** "Use the `--define` flag to inject build-time constants into your executable, such as version numbers ..." with `bun build --compile --define BUILD_VERSION='"1.2.3"' ...` ([Single-file executable, Build-time constants](https://bun.com/docs/compiler/executables)). Values must be JSON-quoted strings ([Build-time constants guide](https://bun.com/docs/guides/runtime/build-time-constants)). The source declares `declare const BUILD_VERSION: string;` or, for plain JS, just references the identifier.
- **The guide's own example computes the version with `git describe --tags --always`**: `--define BUILD_VERSION="\"$(git describe --tags --always)\""`, plus a `Bun.build` script using `await $\`git describe --tags --always\`` (same guide). **[V]**
- **JSON imports are inlined at bundle time.** The loaders doc says the `json` loader "inlines the parsed JSON into the bundle as a JavaScript object" and shows `import pkg from "./package.json"` ([Loaders, json](https://bun.com/docs/bundler/loaders)). **[V]** for bundling. I did not run a compiled binary myself to confirm it, but sessions, grok-cli and gbrain import `package.json` and ship the compiled result **[V]**, so it works in practice.
- **`package.json` is not read at runtime in a compiled binary by default**: "tsconfig.json and package.json loading is disabled"; opt in with `--compile-autoload-package-json` ([executables doc](https://bun.com/docs/compiler/executables)). That matters only if code does a runtime `readFile('package.json')`; a static import is bundled and unaffected. tinbase's comment ("single-binary build has no package.json to read") is the runtime-read failure mode. **[V]** doc, **[I]** that a static import is unaffected by the autoload flag.
- **Windows file version is separate from the in-binary string.** `--windows-icon`, title, publisher, version, description, copyright set file properties; "Except for `hideConsole`, you can't use these flags when cross-compiling because they depend on Windows APIs" ([same doc](https://bun.com/docs/compiler/executables)). Without them, the Windows file version shows Bun's: [can1357/oh-my-pi#14222](https://github.com/can1357/oh-my-pi/issues/14222), closed as completed. **[V]**
- **For this repo (Node ESM `.js`, no version printed today; `grep` over `bin/` and `src/` finds no `--version` handler for the tool itself)**: the portable pattern is crm.cli's, `typeof __APP_VERSION__ === 'undefined' ? (await import('../package.json', { with: { type: 'json' } })).default.version : __APP_VERSION__`, which works under Node and under Bun. **[V]** that crm.cli does this; **[I]** that it fits here, and that Node's JSON import attribute is stable in the Node version the project targets (not checked).

## 3. Where the version comes from

| Approach | Used by (sample) | Tags only on `main` | Fit for develop to main |
|---|---|---|---|
| Hand-bump `package.json` + push tag, CI guard `tag == package.json` | slackcli, genmedia, linear (reads package.json), crm.cli, grok-cli, Archon | Irrelevant: the number comes from a file, not from history | **Good.** Needs only that the bump is on `develop` before the PR. **[I]** |
| Tag is source, CI rewrites `package.json` or generates a constant | muxinc, capa, n8n-cli | Irrelevant | Good, but the `develop` build has no tag to read, so it needs a fallback. **[I]** |
| release-please | sessions, mkdnsite, floci-ui | Tags are created on the target branch by the release PR merge (mkdnsite sets `target-branch: main`) | Works if release-please runs on `main` only; the release PR is a second PR on top of develop to main. **[I]** |
| changesets | playground-cli | Same, runs on main | Adds a `.changeset/*.md` per change. **[I]** |
| semantic-release | keyshade | Needs conventional commits and reachable tags on the release branch | Heavier. **[I]** |
| `git describe` | Bun docs example only | **Counts only tags reachable from the commit.** Verified locally here: `git describe develop` returns `v0.2.2-57-g7b2cc3f`, `git tag --merged develop` ends at `v0.2.2`, while `git tag --merged main` includes `v0.3.0`. **[V]** | Works for dev builds once main is merged back into develop. Needs `fetch-depth: 0` or `fetch-tags` ([actions/checkout README](https://github.com/actions/checkout#checkout-v4): "Only a single commit is fetched by default ... Set `fetch-depth: 0` to fetch all history for all branches and tags"; `fetch-tags` input exists). **[V]** |
| GitVersion | none found | It also derives from tags in history and requires an unshallow clone: "`fetch-depth` in GitHub Actions should set to `0`" ([GitVersion requirements](https://gitversion.net/docs/reference/requirements)); the docs say a tag on the current commit can fix the result ([how it works](https://gitversion.net/docs/learn/how-it-works)). Its Git Flow mode has `develop` produce pre-release versions; I did not find a passage describing what it does with tags that exist only on main, so that part is **[I]** | Heaviest: a config file, `gittools/actions`, and a branching model to match. No Bun project in the sample uses it. |

**Tradeoff in one line:** every approach except hand-bump and release-please-on-main depends on tag reachability, which is exactly this repo's wrinkle (`v0.3.0` is not an ancestor of `develop`). A one-time `git merge main` into `develop` (or a back-merge after each release) removes the wrinkle for `git describe` and GitVersion. **[I]**

**Gaps between the common tag-push pattern and this repo's requirements (all [I], none of the sampled repos does these):**

1. **"Only `main` releases."** `on: push: tags: v*` fires for any branch's tag. A guard such as `git merge-base --is-ancestor "$GITHUB_SHA" origin/main` (with `fetch-depth: 0`) in the first job, or triggering on `push: branches: [main]` instead, is needed. gbrain and release-please take the second route; langwatch builds from the tag ref, not the default branch, and refuses to publish if no tag is given.
2. **Computed version for `develop` builds with no release.** With a hand-bumped `package.json`, a `develop` build prints `0.3.0` unless something is appended. Precedents: opencode `0.0.0-<channel>-<run number>` for previews, langwatch `VERSION="dev"` for dry runs. A semver-valid shape would be `<package.json version>-dev.<run>+<sha>`, but no repo in the sample does exactly that.
3. **Pre-release safety.** genmedia has `dry_run` and `workflow_dispatch` that builds without publishing; linear creates a draft release and flips it only after all assets are attached.

## 4. Cross-compilation

- Targets, from the docs table ([executables doc](https://bun.com/docs/compiler/executables)): `bun-linux-x64`, `bun-linux-arm64`, `bun-windows-x64`, `bun-windows-arm64`, `bun-darwin-x64`, `bun-darwin-arm64`, `bun-linux-x64-musl`, `bun-linux-arm64-musl`. `-baseline` and `-modern` suffixes still parse and resolve to the same x64 binary. **[V]**
- **A single Linux runner can build them all.** The docs describe `--target` as compiling "for a different operating system, architecture, or version of Bun than the machine you're running `bun build` on". Real examples on one Linux runner: mkdnsite (linux-x64, darwin-arm64, windows-x64), mcp-cli, tinbase, playground-cli, langwatch ("One ubuntu job builds ALL targets"). **[V]**
- Why people still use per-OS runners: native smoke tests (slackcli, mux), macOS `codesign` (linear, slackcli), Windows icon (capa), and native addons that need target-specific installs (capa uses `bun install --os --cpu`).
- **Caveats:**
  - Windows icon, title, publisher, version, copyright cannot be set when cross-compiling (docs warning above). capa runs `--windows-icon` only on its Windows runner; on other OSes it uses `--icon`. **[V]**
  - macOS: docs recommend `codesign` with an entitlements plist ([executables doc, Code signing on macOS](https://bun.com/docs/compiler/executables)). Real projects: slackcli ad-hoc signs with `codesign --force --sign -` on a macOS runner; linear signs and notarizes with a Developer ID; modelstudioai re-signs Mach-O files on a Linux runner with `rcodesign` 0.29.0 because "`bun build --compile` leaves an invalid darwin linker signature". **[V]**
  - Windows code signing: none of the files I read signs `.exe`; not investigated further.
  - A cross-compile downloads the target's Bun runtime on first use. [oven-sh/bun#11198](https://github.com/oven-sh/bun/issues/11198) (open on 2026-11-09) fails "Failed to move cross-compiled bun binary into cache directory" when the project is on a different drive from the Bun cache; #25346 was closed as a duplicate. This is a **local Windows** problem (this repo is on `E:`), not a CI one. **[V]** for the issue text, **[I]** that `E:` vs `C:` would trigger it here.

## 5. Common pitfalls

- **macOS signature regressions across Bun versions.** Bun 1.3.12 produced truncated or corrupt code signatures, so macOS arm64 binaries were killed on launch ([oven-sh/bun#29120](https://github.com/oven-sh/bun/issues/29120), [#29306](https://github.com/oven-sh/bun/issues/29306), [#29361](https://github.com/oven-sh/bun/issues/29361)); the fix, #29272, shipped in 1.3.13. slackcli's workflow comment cites this and pins 1.4.1. **[V]**
- **Bun 1.4.0 on macOS 27.** [oven-sh/bun#39758](https://github.com/oven-sh/bun/issues/39758) (closed not planned, re-filed) and [#39764](https://github.com/oven-sh/bun/issues/39764) (**open**, labels `bug`, `needs triage`, no comments when read) report 1.4.0 `--compile` binaries SIGKILL'd on macOS 27 while 1.3.14 artifacts run. I found no fix reference, so whether 1.4.1 to 1.4.4 fixed it is **unverified**. Test the macOS binary on your target OS before shipping. gbrain and thunderbolt use 1.4.4; slackcli uses 1.4.1, citing that 1.4.1 is "the first release whose `--bytecode` cross-compiles to Windows x64".
- **Version mismatch.** Documented fixes in the wild: slackcli's `verify-version` job (issue #81 in that repo), genmedia's "Verify package version" step, Archon asserting the built binary reports the tag. A Windows-specific variant: slackcli's PowerShell runner did not understand `${VAR#prefix}`, so the Windows binary had an empty version (#443); fix is `shell: bash` on every step. **[V]**
- **Pinning `oven-sh/setup-bun`.** The action README: `bun-version` accepts `latest`, `canary`, `1.0.x` or exact; `bun-version-file` accepts `package.json`, `.bun-version`, `.tool-versions`; default is the `packageManager` or `engines.bun` field of `package.json`, else `latest` ([setup-bun README](https://github.com/oven-sh/setup-bun#readme)). Of the sampled workflows, about half use `latest`; the ones that pin are the ones with signing or bytecode issues (slackcli, gbrain, thunderbolt, capa, modelstudioai, genmedia via `.bun-version`, opencode via `packageManager`). Bytecode is tied to the Bun version that emits it (slackcli comment). **[V]**
- **Binary size.** The docs call the binary "way too big" and offer `--minify`; `--bytecode` trades size for startup ([executables doc](https://bun.com/docs/compiler/executables)). Most sampled projects use `--minify`. Not measured here.
- **Runtime reads of `package.json`, `.env`, `bunfig.toml`.** Compiled binaries do not autoload `package.json`/`tsconfig.json` by default and do autoload `.env`/`bunfig.toml`; Archon passes `--no-compile-autoload-dotenv --no-compile-autoload-bunfig`, gbrain passes `--no-compile-autoload-bunfig`. **[V]** for the flags in the workflows; whether this matters for yt-transcript is **[I]**.

## Recommended shape for this repo (all of it [I]: a synthesis of the sampled workflows, not a copy of one)

1. Keep hand-bumping `package.json` on `develop` (variant b), exactly as slackcli and genmedia do.
2. Release workflow in the slackcli shape: matrix with `--target`, `--define` from the tag, `softprops/action-gh-release@v2` (or v3), plus a `verify-version` job.
3. Add the one thing no sampled repo does: fail unless the tagged commit is an ancestor of `origin/main` (needs `fetch-depth: 0`), or trigger on push to `main` and create the tag with the release (gbrain, mkdnsite shape).
4. For non-release builds, `--define` a computed string (`<package.json version>-dev.<run>+<short sha>`), as opencode and langwatch do for previews.
5. Pin Bun in `.bun-version` (genmedia) or `packageManager` (opencode), and smoke-test `./dist/yt-transcript --version` per target (slackcli, muxinc).
6. Merge `main` back into `develop` once so `git describe` is sane for local builds.
